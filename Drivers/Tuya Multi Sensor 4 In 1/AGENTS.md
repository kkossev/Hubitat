# Tuya Multi Sensor 4 In 1 — Driver Guide for AI Agents

This folder contains a **Hubitat Elevation (HE) Zigbee driver** (Groovy) for a large family of
Tuya-based PIR motion sensors and multi-sensors (motion / temperature / humidity / illuminance),
plus a few non-Tuya brands (Sonoff, OWON, SiHAS, IMOU, Espressif, TUYATEC RH3040).
Author: Krassimir Kossev. License: Apache 2.0.

Community thread: https://community.hubitat.com/t/release-tuya-zigbee-multi-sensor-4-in-1-pir-motion-sensors-w-healthstatus/92441
Wiki: https://github.com/kkossev/Hubitat/wiki/Tuya-Multi-Sensor-4-In-1

**Backlog:** there is one consolidated work-list — [TODO.md](TODO.md) in this folder. It holds the
device-support backlog, the feature backlog, and the reviewed bug list with exact locations, fixes
and verification steps. If you were asked to fix bugs or add a device, work from that file — do not
re-derive the findings. (`BUGS.md` was merged into it and retired on 2026-08-03; released history
lives in [CHANGELOG.md](CHANGELOG.md) and the git log.)

**Never mark an item done on your own judgement** — ask the user whether the fix is confirmed on the
hub, and only then update its status. See the workflow rules below.

**Important scope note:** mmWave radar support was **moved out** of this driver into the separate
"Tuya Zigbee mmWave Sensor" driver (see README.md link). All radar profiles still present here are
marked `isDepricated: true` and only show a warning directing users to the mmWave driver.
The one exception is the newer `TS0601_TZE284_4IN1` profile (a 4-in-1 mmWave+PIR combo added in v3.5.6),
which is active in this driver.

### Editing workflow

**Golden rule: agents edit SOURCE files only. Never write to `Tuya Multi Sensor 4 In 1.groovy`.**
That bundle is generated by the maintainer immediately before publishing to GitHub; an agent
editing it creates a file that will be silently overwritten at the next release, and risks
diverging from the real source. This matches root [AGENTS.md](../../AGENTS.md) §2 rule 2 and §4
("never hand-edit the bundle's logic"). Do not "mirror", "sync", or "regenerate" the bundle, and do
not renumber its `// library marker` suffixes.

- **Driver-specific change** (device profiles, custom* methods, metadata): edit
  **`Tuya Multi Sensor 4 in 1 (V3).groovy`** — that file only. Nothing else needs touching.
- **Library change** (anything inside commonLib / deviceProfileLib / illuminanceLib / …): edit
  **`C:\work\Hubitat\Libraries\<lib>.groovy`** — that file only. The V3 source picks it up through
  its `#include`, so it needs no edit either. Remember the same library is embedded in many other
  drivers in this repo: state **which drivers are affected and whose bundles are therefore pending
  regeneration**, and let the user decide when to rebuild them.
- **Reading the bundle is fine and often necessary** — TODO.md line references ("amalg NNNN") point
  into it, and library code there is the region whose lines end with
  `// library marker kkossev.<libName>, line N`. Read, quote, cite. Just don't write.
- After a change, report it as *"source edited; bundle regeneration pending (maintainer)"*.
- **Only when the user says so** (release point, never after an individual bug fix — root
  [AGENTS.md](../../AGENTS.md) §2 rule 4): bump `version()` and `timeStamp()` at the top, add a
  `ver. x.y.z  date  kkossev - ...` comment line to the header history, and mirror the entry in
  README.md.
- Repo and branch policy: see root [AGENTS.md](../../AGENTS.md) §1 — `C:\work\Hubitat` **is** a git
  clone of `kkossev/Hubitat` on the `development` branch, and `development` is the single source of
  truth (`main` is only a compatibility entry point).

## 2. Runtime architecture (V3 / "deviceProfilesV3")

The driver is **data-driven**. Almost all per-device behavior lives in one big
`@Field static final Map deviceProfilesV3` (starts ~line 148 of the expanded file). The generic
libraries interpret that map; only genuinely device-specific logic lives in `custom*` hook methods.

### 2.1 Included libraries (bottom of the expanded file, in this order)

| Library | Ver (in 3.6.1 build) | Purpose |
|---|---|---|
| `deviceProfileLib` | 3.5.8 | The heart: profile matching, dynamic preferences, `setPar`/`sendCommand`, Tuya DP + ZCL attribute decoding driven by the profile map. |
| `commonLib` | 4.1.1 | `parse()` entry point, Zigbee message routing per cluster, Tuya cluster 0xEF00 protocol, health check / ping / RTT, stats, `initialize()`/`configure()`/`updated()` scaffolding, `sendZigbeeCommands()`, logging helpers (`logDebug/logInfo/logWarn/logTrace`). |
| `batteryLib` | 3.2.4 | Battery % and voltage events, delayed battery reporting. |
| `temperatureLib` | 3.3.2 | `handleTemperatureEvent()`, offsets, °C/°F. |
| `humidityLib` | 3.3.1 | `handleHumidityEvent()`. |
| `illuminanceLib` | 3.2.2 | `handleIlluminanceEvent()`, lux correction coefficient, illuminance threshold filtering. |
| `iasLib` | 3.2.2 | IAS Zone (cluster 0x0500) enrollment and zone status parsing. |
| `motionLib` | 3.2.3 | `handleMotion(boolean)`, `sendMotionEvent()`, `resetToMotionInactive()` (software "motion reset" timer), `setMotion` command, `getSecondsInactive()`, `invertMotion` handling. |

### 2.2 The `custom*` hook contract

`commonLib` calls hook methods **only if the main driver defines them** (via `this.respondsTo(...)`).
The main driver (lines ~748–1180) implements:

- `customParseIasMessage(String)` — IAS zone status → `handleMotion()` (alarm1 = motion).
- `customParseOccupancyCluster(Map)` — cluster 0x0406 (OWON/Sonoff occupancy); first tries
  `processClusterAttributeFromDeviceProfile()`, falls back to attr 0000=occupancy, 0020=fadingTime, 0022=radarSensitivity.
- `customProcessTuyaDp(descMap, dp, dp_id, fncmd, dp_len)` — called by commonLib for each Tuya DP
  report. Tries `processTuyaDPfromDeviceProfile()` (deviceProfileLib, matches the profile's `tuyaDPs`
  list); on failure falls through to `localProcessTuyaDP()` which hard-codes legacy DPs
  (1=motion, 4/25=battery, 7=temp, 8=humidity, 9=sensitivity, 10=keepTime, 101=motion…).
- `customProcessDeviceProfileEvent(descMap, name, valueScaled, unitText, descText)` — called by
  deviceProfileLib's `processFoundItem()` once a DP/attribute is decoded; dispatches by attribute
  name: `motion`→`handleMotion`, `temperature`→`handleTemperatureEvent`, `humidity`, `illuminance`,
  `pushed`→`sendButtonEventToChild()`; everything else becomes a generic `sendEvent`.
- `customRefresh()` / `refreshFantem()` — refresh list comes from the profile's `refresh:` list
  (names can be profile items or method names, e.g. `refreshAllIas`, `queryAllTuyaDP`, `refreshFantem`
  = Tuya "magic" `zigbee.command(0xEF00, 0x07, '00')`).
- `customParseOnOffCluster(Map)` / `customParseLevelControlCluster(Map)` — clusters 0x0006 / 0x0008
  cluster-specific commands sent **by** a device button; both call `processButtonZclCommand()`, which
  maps them through the profile's `buttons.zclCommands` and forwards the result to the button child
  device. Without a `buttons:` map they only log at debug level (that is also what keeps the
  "Missing standardParseOnOffCluster handler" warnings out of the log).
- `customCreateChildDevices(fullInit)` — called from commonLib's `initializeVars()`; calls
  `syncButtonChildDevice()`, which creates / updates / deletes the button child device
  (`Generic Component Button Controller`, DNI `<device.id>-BTN`) according to the profile's
  `buttons:` map. Also called at the end of `customUpdated()`, because `checkDriverVersion()` runs
  `initializeVars()` only when the driver version string changed.
- `customUpdated()` — applies `forcedProfile` switch, deletes `distance`/`all` states, then
  `updateAllPreferences()` (writes every profile preference to the device), then
  `syncButtonChildDevice()`.
- `customConfigureDevice()` — builds binding/reporting commands from the profile's `configuration:`
  map (keys like `'0x0001'`, `'0x0406'`, `'custom':'configureEspressif'`); IAS enroll for `isIAS` devices.
- `customInitializeVars(fullInit)` / `customInitEvents(fullInit)` — defaults; note `invertMotion`
  defaults to **true for 2-in-1** (`is2in1()`, `_TZE200_3towulqd` reports inverted motion).
- `formatAttrib()` / `addToAttr()` — builds the optional `all` status attribute (one string with all values).

### 2.3 Anatomy of a device profile entry

```groovy
'PROFILE_KEY' : [
    description   : 'human-readable name',
    models        : ['TS0601'],                    // fallback match
    device        : [type:'PIR'|'radar', isIAS:true/false,
                     powerSource:'battery'|'dc'|'mains',
                     isSleepy:true/false,          // sleepy => can't be configured except right after wake
                     isDepricated:true],           // optional; blocks preferences, shows warning
    capabilities  : ['MotionSensor':true, 'Battery':true, ...],
    preferences   : ['motionReset':true,           // true = generic pref from a library
                     'sensitivity':'9',            // '9' = Tuya DP number 9
                     'keepTime':'0x0500:0xF001'],  // ZCL cluster:attribute
    commands      : ['resetStats':'resetStats', ...],   // exposed via sendCommand
    fingerprints  : [[profileId:'0104', inClusters:'...', model:'TS0202',
                      manufacturer:'_TZ3210_zmy9hjay', deviceJoinName:'...'], ...],
    tuyaDPs       : [[dp:1, name:'motion', type:'enum', rw:'ro', min:0, max:1,
                      defVal:'0', scale:1, map:[0:'inactive',1:'active'],
                      description:'Motion'],
                     // writable DPs add: dt:'01'/'02' (Tuya data type), tuyaCmd:04,
                     // title:'<b>..</b>' (makes it a preference), step, unit, preProc:'fnName'
                     ...],
    attributes    : [[at:'0x0500:0x0013', name:'sensitivity', ...]],  // ZCL-based params
    refresh       : ['refreshAllIas','sensitivity','keepTime','refreshFantem'],
    configuration : ['battery':false, 'custom':'configureEspressif',
                     '0x0406':['bind':true],                            // bind only
                     '0x0402':['reporting':[10,3600,50]]],              // configureReporting [minTime, maxTime, delta] - it binds too
    buttons       : [numberOfButtons:1,                          // optional; devices with a built-in button
                     supportedButtonValues:['pushed','held'],    // the same set for every button
                     zclCommands:['0x0006:0x02':[1,'pushed']],   // 'cluster:command[:firstDataByte]' -> [buttonNo, event]
                     tuyaDPs:[101:1]],                           // Tuya DP -> buttonNo (event name from that DP's enum map)
    spammyDPsToIgnore : [9], spammyDPsToNotTrace : [9,103],   // radar distance spam control
],
```

Key semantics a new agent must know:
- **Fingerprint → profile matching** happens at pairing (and via `setDeviceNameAndProfile()`);
  the profile key is stored in `state.deviceProfile`. Users can override with the `forcedProfile` preference.
- **Preferences are generated dynamically**: deviceProfileLib's `inputIt(key)` turns each entry of
  `DEVICE.preferences` into an `input()` using the matching `tuyaDPs`/`attributes` item
  (its `title`, `type`, `min/max`, `map`). No hard-coded preference blocks per device.
- `scale` divides incoming values (e.g. temperature `scale:10`), and multiplies outgoing writes.
- `preProc:'fnName'` transforms the raw value before scaling (e.g. `tuyaToBatteryLevel`).
- `DEVICE` is a getter (deviceProfileLib) returning `deviceProfilesV3[state.deviceProfile]`.
- The `'---'` entry is just a visual separator in the forcedProfile drop-down; `'UNKNOWN'` is the
  fallback profile and doubles as a documented template for new entries (~line 715).
- **Attribute reporting**: `customConfigureDevice()` runs `bindAndConfigureReporting()` for clusters
  0x0400 / 0x0402 / 0x0405 / 0x0406. Each binds when its `configuration:` key exists (unless
  `'bind':false`), and additionally sends a `configureReporting` when that key carries a
  `'reporting':[minTime, maxTime, delta]` list. `delta` is in ZCL units — 0.01 °C, 0.01 %RH. If the
  profile also declares the **`'ReportingConfiguration': true`** capability, the temperatureLib
  preferences *Minimum/Maximum time between reports* (Advanced Options) override the profile's
  min/max — but **only when they differ from the library defaults** (`DEFAULT_MIN_REPORTING_TIME` 10,
  `DEFAULT_MAX_REPORTING_TIME` 3600); those preferences always hold a value, so without that guard
  the profile numbers could never take effect. Note that `zigbee.configureReporting()` emits its own
  `zdo bind`, so the helper skips the explicit bind whenever a `reporting:` list is present — an entry
  with `reporting:` therefore needs no `'bind'` key at all, and setting one there has no effect. The new
  intervals reach the device only on **Configure**, and only while a sleepy device is awake.
- **`buttons:` never adds capabilities to the parent driver.** The button events go to a child device
  running the Hubitat inbuilt `Generic Component Button Controller`; the parent has no
  `PushableButton` capability and no `pushed` attribute, and `buttonLib` is deliberately not
  included. Hex keys in `zclCommands` are **uppercase**. The Tuya DP path is intercepted in
  `customProcessTuyaDp()` *before* `processTuyaDPfromDeviceProfile()`, because `processFoundItem()`
  returns early for values that are neither a parent attribute nor a preference.

### 2.5 Driver metadata specifics

- Driver name on the hub: **`Tuya Multi Sensor 4 In 1 (V3)`**, namespace `kkossev`, `singleThreaded: true`.
- Only `MotionSensor` capability is declared statically; everything else (Temperature, Humidity,
  Illuminance, Battery, Tamper…) is handled via events per profile `capabilities` (HE allows
  sending events for undeclared capabilities; Rule Machine visibility relies on the attributes).
- Fingerprints are emitted **dynamically** in `metadata{}` by iterating `deviceProfilesV3`
  (skipping deprecated profiles).
- Custom commands: `sendCommand('name','value')` and `setPar('parameter','value')` — generic
  gateways into the profile's `commands` and `preferences` maps. `setMotion(active/inactive)` from motionLib.
- Custom attributes: `all`, `distance` (obsolete), `sensitivity`, `keepTime`, `fadingTime`,
  `humanMotionState`, `illumState`, `ledEnable`, `reportingTime4in1`, `WARNING`, etc.

## 3. Common maintenance tasks (recipes)

### Add support for a new device (most frequent request)
1. Get `model` + `manufacturer` from the user (HE Device Details → Data section), plus the
   zigbee-herdsman-converters (zigbee2mqtt) source link if available — profiles here regularly cite it.
2. If the device behaves like an existing group → just append a fingerprint map to that profile's
   `fingerprints` list (copy an adjacent line; keep `deviceJoinName` descriptive).
3. If it needs different DPs/preferences → create a new profile key. Model it on `TS0601_2IN1`
   (Tuya EF00 device) or `TS0202_MOTION_IAS_CONFIGURABLE` (IAS device). Get DP numbers from
   zigbee-herdsman-converters `src/devices/tuya.ts`.
4. Set `device.isIAS`, `powerSource`, `isSleepy` correctly — they drive configuration, health check
   and pairing behavior. Battery-powered sleepy devices only accept config right after a wake/pairing.
5. Bump versions (see Editing workflow), test-compile on a hub, update README table + history.

### Radar/mmWave request
Do **not** add radars here — direct to the "Tuya Zigbee mmWave Sensor" driver
(https://community.hubitat.com/t/alpha-tuya-zigbee-mmwave-sensors-moving-the-code-from-the-tuya-4-in-1-driver/137410).
(Exception already made: `TS0601_TZE284_4IN1`.)

### Debugging a device that sends wrong/no events
- Have the user enable debug logging (24 h auto-off) and capture `parse()` logs.
- `NOT PROCESSED from deviceProfile` warnings mean the DP is missing from the profile's `tuyaDPs` →
  add it (even read-only, `rw:'ro'`) to silence and decode.
- Motion inverted? Check `invertMotion` preference (auto-true for 2in1 profiles).
- Motion never resets? The `motionReset` preference arms `resetToMotionInactive()` software timer.
- `_DEBUG` / `_TRACE_ALL` static flags at the top enable test commands and full tracing.

### Gotchas / historical traps
- Groovy method-size limit: HE compiles methods > 64 KB fail ("Method too large") — that's why
  parsing is decomposed; keep new switch/case blocks small.
- `@Field static` maps are shared across all devices using the driver on a hub — never mutate
  `deviceProfilesV3` at runtime (caused `CloneNotSupportedException` fix in 3.5.0).
- HE platform 2.4.1.x has a decimal-preference range bug — workaround already in 3.5.1/deviceProfileLib 3.4.3.
- Spelling quirks are intentional/legacy: "depricated", "ESRESSIF", "Huidity" appear in code as keys
  and strings — do not "fix" map keys without updating every reference.
- `packageManifest.json` version must match the released driver version for HPM updates to trigger.
