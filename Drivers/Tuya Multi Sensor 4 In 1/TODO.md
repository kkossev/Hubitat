## Release policy (read before touching any manifest)

**Never bump `packageManifest.json`, and never file its version lag as a bug.** The lag is
deliberate: kkossev raises the HPM manifest rarely, only for major fixes, because he does not own
every supported device and cannot test every change. Manifest `location` URLs point at
`development`, so any bump instantly serves the current branch state to *every* HPM user. Users
wanting a newer build are told to update manually or run an HPM **Repair**. Full policy in the root
[PUBLISHING.md](../../PUBLISHING.md) §*HPM manifest version policy*.

A user reporting "HPM still offers me an older version" is describing expected behaviour.

`Tuya Multi Sensor 4 in 1 (V3).groovy`; library fixes go in `C:\work\Hubitat\Libraries\<lib>.groovy`.

Hubitat quirk relied on below: bare undefined *identifiers* resolve to `null` in HE drivers (no

### A — Functional bugs

#### A6 — ASK USER — `TS0202_MOTION_SWITCH` button events are dead

The profile defines dp:101 `pushed` and `customProcessDeviceProfileEvent()` has a `'pushed'` case,
but: (1) the driver declares no PushableButton/DoubleTapableButton/HoldableButton capability and no
`pushed` attribute, so `processFoundItem()` returns early and the handler is never reached;
(2) `buttonEvent()` does not exist anywhere in the driver and would throw
`MissingMethodException`; (3) the handler logs undefined `value`/`valueCorrected`.

Fix options — **kkossev's decision, ask before implementing**: (a) add button capabilities plus a
minimal `buttonEvent()`, using the standalone `Tuya_Motion_Sensor_and_Scene_Switch.groovy` v1.4.2 in
this folder as the reference; or (b) remove dp:101/`switch` from the profile and document that
scene-switch users need the clone driver.

#### A8 — VERIFY ON DEVICE — `TS0601_TZE284_4IN1` `pirSensitivity` data type

Profile `TS0601_TZE284_4IN1`, dp:9 uses `dt:'01'` (bool) with a 3-value enum map. Tuya DP types are
01=bool, 02=value, 03=string, 04=enum, so enum writes should be `dt:'04'`. Verify against
zigbee-herdsman-converters (`_TZE284_gnpflcoq`) and test that sensitivity writes are accepted.

#### A9 — VERIFY ON DEVICE — TUYATEC RH3040 battery percentage probably halved

`isTuya()` matches only model `TS*` + manufacturer `_T*` (or HOBEIAN), so `RH3040`/`TUYATEC-*` falls
into the standard-ZCL branch of `standardParsePowerCluster()`, which divides attribute 0x0021 by 2.
z2m treats TUYATEC-manufacturer devices as `dontDividePercentage`.

Verify with a real RH3040 or against z2m source, then either extend `isTuya()` to cover `TUYATEC-*`
(careful — the library is shared by many drivers) or special-case it in the battery path.

#### A10 — ASK USER + VERIFY — `tuyaToBatteryLevel()` inflates genuine 1–4 % levels

Raw 0→100 %, 1→75 %, 2→50 %, 3→25 %, 4→100 %. That mapping is correct only for devices reporting
battery *state* (full/high/med/low/USB) and wrong for devices reporting a true percentage over dp:4
— e.g. a TS0601 2-in-1 nearly empty at 3 %.

Fix direction: make the mapping opt-in per profile (a `preProc` used only where state-style
reporting is confirmed) rather than the global default in `handleTuyaBatteryLevel()`. Needs
kkossev's decision on which profiles keep it. This is the known "3-in-1 shows 4 %" README TODO.

### B — Logic and robustness

#### B2 — OPEN (half done) — Refresh does not force humidity events

Pressing Refresh re-reads the device, but an unchanged value is swallowed by the delta filter and no
event is sent. Fixed for temperature (temperatureLib 3.3.1) and for illuminance (3.5.8);
**humidityLib line 56 still has no `isRefresh` bypass.**

Design decision already made for illuminance: `isRefresh` must bypass **both** the delta filter *and*
the minimum reporting interval, so a Refresh publishes immediately rather than being queued —
`if (isRefresh || timeElapsed >= minTime)` on the send branch, plus `!isRefresh &&` on the delta
guard.

**This means temperatureLib 3.3.1 is itself incomplete**: it bypasses only the delta filter, so a
Refresh within 10 s of the last temperature event is still delayed. Aligning all three libraries on
the two-gate bypass is the remaining work.

#### B3 — DONE, hub confirmation pending — `inputIt()` never propagated preference defaults

`if (input.defVal != null) { input.defVal = foundMap.defVal }` tested the never-set `input.defVal`,
so it was always skipped — and `defVal` is not a valid `input()` key anyway. Fixed 2026-08-03 to
`if (foundMap.defVal != null) { input.defaultValue = foundMap.defVal }`. Additive only: no commands
sent, no state touched, just the pre-filled default on an unsaved field.

**Caveat to verify:** for `enum` preferences `foundMap.defVal` is a **string** (e.g. `defVal:'0'`)
while `input.options` is keyed by **integers**. Hubitat is usually lenient, but this needs eyeballing.

**Test plan:**
1. On a device with an **unsaved** number/decimal preference, the field should now show the
   profile's declared default instead of blank.
2. On a device with an **unsaved enum** preference (e.g. `vSensitivity` on `TS0601_PIR_AIR`), the
   dropdown should pre-select the correct labeled option — not blank, not the wrong one.
3. On a device with **saved** values, those must still display and must not be overwritten.

#### B4 — OPEN — `TS0202_4IN1` advertises a `reportingTime4in1` command that cannot execute

The profile `commands` map includes `'reportingTime4in1':'reportingTime4in1'`, but no such method
exists, so `sendCommand('reportingTime4in1', x)` throws (caught, logged, returns false). Remove the
entry or route it through `setPar('reportingTime4in1', val)`.

#### B5 — OPEN — unquoted method name disables the deviceProfile fallback in commonLib

commonLib line 827: `if (this.respondsTo(processTuyaDPfromDeviceProfile))` — a bare identifier
evaluating to null. Should be `this.respondsTo('processTuyaDPfromDeviceProfile')`. Masked in this
driver because `customProcessTuyaDp()` always returns true, but live for other drivers.

#### B6 — OPEN — `return` inside `.each` closures does not exit the method

- `getDeviceNameAndProfile()` (deviceProfileLib line 878): `return [deviceName, deviceProfile]` only
  exits the closure — iteration continues and a later overlapping fingerprint could overwrite the
  match. Rewrite with a `for` loop plus labeled break, or `find`.
- `validateAndFixPreferences()`: `return false` inside `.each` only skips an iteration; the method
  still returns true. Rewrite with `for` if the return value matters.

#### B7 — OPEN — `deviceProfilesV3defaults` referenced but never defined

deviceProfileLib line 727, added in lib 3.5.5. Works only via HE's null-resolution quirk, breaks
under `@CompileStatic`, and the "defaultCommands" feature silently does nothing here. Define an
empty `@Field static final Map deviceProfilesV3defaults = [:]` in the main driver, or guard with
`this.hasProperty(...)` in the library.

#### B8 — OPEN — `divideBy10()` only divides values > 10

deviceProfileLib lines 310–313: values 0–10 pass through unscaled (an old IJXVKHD0 patch). No active
profile uses it, but it is a landmine for reuse. Fix, or rename to `divideBy10Legacy`.

#### B9 — OPEN — `formatAttrib()` sends the oversized `all` event before checking the 64-char limit

`updateAttr('all', attrStr)` runs before the `length() > 64` check, producing two events. Move the
length check before the first `updateAttr`.

### Considered and rejected — do not re-open

#### A11 — NOT A BUG — `invertMotion` defaults to true for the whole `TS0601_2IN1*` family

Closed 2026-08-03. Three independent implementations agree that **dp1 == 0 means occupied**: z2m uses
`tuya.valueConverter.trueFalse0` for `ZG-204ZL`, `TS0601_pir` (Haozee) and `ZPIR-10` (Treatlife),
with the helper at `src/lib/tuya.ts:1488` being `from: (v) => v === valueTrue`; and the ZHA quirk
`zhaquirks/tuya/tuya_motion.py:1156` decodes dp 1 with `converter=lambda x: x == 0`.

The profile's `[0:'inactive', 1:'active']` map looks wrong in isolation and only composes correctly
once `invertMotion` is taken into account — that is the trap that produced this false positive.

**Do not narrow `is2in1()`** to exclude `TS0601_2IN1_MYQ_ZMS03`; that was the original suggested
"fix" and it would break motion reporting on every device in that group.

Optional tidy-up: mirror this reference as a code comment next to `is2in1()` or the dp:1 entry.

#### A15 — NOT A BUG — the `packageManifest.json` version lag is deliberate

Filed in error 2026-08-03 and retracted the same day. See *Release policy* at the top of this file.
Do not re-file, here or in any other driver folder.
